結論(TL;DR)

この文書は、SCD40センサー(CO2・温度・湿度)の値をAWS IoT Coreへ定期送信するGreengrassカスタムコンポーネント scd40-publisher を実装するための、6タスクの実装計画です。Pythonのバージョンは3.13です。

リポジトリをuvワークスペースのモノレポとして整備し、ビルドスクリプトまで揃えます。各機能はテストを先に書いてから実装する進め方です。

センサー読み取りや送信が失敗してもプロセスは落とさず、ログを残して次の測定サイクルへ進む設計です。アーティファクト用のS3バケットが未作成のため、デプロイ関連は今回の対象外です。AWS側リソースの作成とCI導入も対象外です。

要点

  1. 複数コンポーネントを1つで管理するために、リポジトリをuvワークスペースのモノレポにし、コンポーネントを専用ディレクトリの下へ追加していく形にします。
  2. デバイス側の構成を増やさないために、Raspberry Piにはuvを入れず、ビルド時に書き出した依存一覧をpip3だけで導入します。
  3. 実機なしでテストできるように、I2CセンサーとGreengrass IPCへの依存は「実物を生成する関数」に閉じ込め、テストは偽物のオブジェクトで実行ロジックを検証します。
  4. 測定を止めないために、センサー読み取りの失敗も、IoT Coreへの送信失敗もログに残して次のサイクルへ進みます。送信に失敗したデータは破棄し、ローカルキューは持ちません。
  5. 異常時の復旧をGreengrassに任せるために、起動時にI2Cデバイスを検出できなければプロセスを終了し、再起動はライフサイクル管理に委ねます。
  6. 設定を実行に反映するために、レシピで定義したトピック名と測定間隔(既定は60秒)を環境変数経由でプログラムへ渡します。
  7. 配布物を同じ手順で作れるように、ビルドをスクリプト化し、ソース・レシピ・依存一覧をzipにまとめます。デプロイはS3バケットが未作成のため、今回は含めません。

判断・対応が必要な点

元文書に「未決」「要確認」と明記された項目はありません。以下は、今回の範囲の確認事項と、あとまわしにした項目です。

  • デプロイは別タスクに回す: アーティファクト用のS3バケットが現在存在しないため、デプロイスクリプト、コンポーネント登録、デプロイ作成、デプロイ手順書は今回作りません。設計書のデプロイ関連の記述は、S3バケットの準備後に実施します。
  • レシピの仮の値はそのまま: バージョンとアーティファクトのURIは仮の値のままです。デプロイ処理を整備する際に、実際の値へ書き換える仕組みを追加します。
  • 対象外の確認: AWS側リソースの作成とCI(GitHub Actionsなど)の導入も、本タスクのスコープ外です。
  • レビューで確認する4点:
    • センサー読み取り失敗時にプロセスが落ちず、次の測定サイクルで継続すること。
    • IoT Core送信失敗時にログのみを記録してデータを破棄し、例外を伝播させないこと。
    • 起動時にI2Cデバイスを検出できなければ終了し、再起動をGreengrassに委ねること。
    • レシピのトピック名・測定間隔が環境変数経由で実行に正しく反映されること。
実機のセンサーとGreengrass IPCを生成する2つの関数(create_hardware_sensor、create_ipc_publisher)は、計画上どのテストからも呼び出されません。実機での動作は自動テストの対象外です。

詳細

概要(ゴール・構成・技術スタック)

ゴール: リポジトリをuvワークスペースのモノレポとして整備し、SCD40センサーの値をAWS IoT Coreへ定期送信するコンポーネントを実装します。ビルドスクリプトとドキュメントも揃えます。デプロイはS3バケットが未作成のため対象外です。

構成: ルートにuvワークスペースを置き、コンポーネントはsrcレイアウトのPythonパッケージとして実装します。ハードウェアとIPCへの依存は実物を生成するファクトリ関数に隔離します。ビルドスクリプトでは、外部コマンド実行を差し替え可能にしてテストします。

技術スタック: Python 3.13、uv、pytest、adafruit-circuitpython-scd4x、adafruit-blinka、awsiotsdk、PyYAML。

設計書: docs/superpowers/specs/2026-09-29-greengrass-scd40-component-setup-design.md

実行する場合は、superpowers:subagent-driven-development(推奨)または superpowers:executing-plans を使い、チェックボックス付きのステップをタスク単位で進めます。
全体の制約
  • パッケージ管理はuvを使います。Raspberry Pi側にはuvを入れず、pip3のみで依存を導入します。
  • モノレポ構成とし、コンポーネントは components/ 配下にディレクトリを追加して管理します。
  • S3バケット、IoT Thing/Thing Group、IAMポリシーの作成はスコープ外です。
  • デプロイ関連(デプロイスクリプト、S3アップロード、コンポーネント登録、デプロイ作成、デプロイ手順書)はスコープ外です。アーティファクト用S3バケットが現在存在しないためです。
  • CI導入はスコープ外です。
  • Pythonのバージョンは3.13とします。
  • IoT Coreへの送信失敗時はローカルキューを持たず、ログ記録のみでデータを破棄します。
  • 測定間隔の既定値は60秒、MQTTトピックの既定値は greengrass-components/scd40-publisher/<thingName>/telemetry です。
ファイル構成
  • リポジトリのルート: ワークスペース設定、Pythonバージョン指定、除外設定、README。共有の開発用依存(pytest、PyYAML)もここで持ちます。
  • ルートのテスト置き場: レシピの構造検証と、ビルドスクリプトの単体テスト。
  • スクリプト置き場: ビルド(依存一覧の生成とzip化)の1本。
  • コンポーネントのディレクトリ: 個別の依存定義、Greengrassレシピ、ソース(センサー読み取り、IoT Core送信、エントリポイントの3モジュール)、それぞれのテスト。
タスク1: uvワークスペースとコンポーネント雛形の作成

まず「パッケージをimportできる」という失敗するテストを書き、雛形を作って通します。

  • ルートの設定で、components/ 配下をワークスペースのメンバーにし、pytestがスクリプト置き場とコンポーネントのテストを見つけられるようにします。
  • Pythonは3.13を指定し、仮想環境やビルド成果物などをGit管理から除外します。
  • コンポーネント側には、センサー・Adafruitライブラリ・AWS IoT SDKの依存と、hatchlingによるビルド設定を置きます。
  • 依存を uv sync で解決し、テストの合格を確認します。
  • READMEに、リポジトリの役割、セットアップ手順、コンポーネント一覧、ビルド手順を追記します。デプロイは「未整備(S3バケット用意後に追加)」と記します。
タスク2: センサー読み取りロジック(TDD)

SCD40から測定値を1回分取得する部分です。テストは2件です。

  • 測定値は、CO2濃度、温度、湿度の3項目をまとめた1つのデータとして扱います。
  • 定期測定の開始は最初の読み取り時に1回だけ行います。
  • データの準備が整うまで、一定間隔(既定1秒)で待ってから値を返します。
  • 実機のI2Cとセンサーを組み立てる処理は別関数に分け、必要になったときに初めて関連ライブラリをimportします。
タスク3: AWS IoT Coreへのパブリッシュ(TDD)

測定値をIoT Coreへ送る部分です。テストは1件で、偽のIPCクライアントに渡された内容を検証します。

  • 送信内容は、CO2・温度・湿度に現在時刻(UTC)を加えたJSONです。
  • 設定されたトピックへ送ります。
  • 実機ではGreengrass IPCで接続し、QoSは「少なくとも1回」、応答待ちは10秒とします。
  • 実際のIPC接続を作る処理は別関数に分け、テストからは呼びません。
タスク4: エントリポイントと実行ループ(TDD)

測定と送信を繰り返す本体です。テストは6件です。

  • 1サイクル: 読み取りに成功したら送信します。読み取りに失敗したらログを出して戻ります。送信に失敗したらログを出してそのデータを破棄します。いずれも例外は外へ出しません。
  • 起動: センサーの初期化に失敗したら、ログを出して終了コード1で終了します。
  • 設定: トピック名は GG_TOPIC_NAME(既定 greengrass-components/scd40-publisher/default/telemetry)、測定間隔は GG_MEASUREMENT_INTERVAL_SECONDS(既定60)の環境変数から読みます。
  • ループ: サイクルの間で待機します。テストのために、実行回数の上限と待機処理を差し替えられます。上限に達した最後のサイクルの後には待機しません。
  • テストでは、正常系、読み取り失敗、送信失敗、初期化失敗による終了、回数を限った実行、環境変数による上書きを確認します。
タスク5: Greengrassレシピと検証テスト

コンポーネントの定義ファイルです。テストは3件で、構造だけを検証します。

  • コンポーネント名は com.example.Scd40Publisher です。
  • 既定設定として、トピック名(Thing名を埋め込む形)と測定間隔(60秒)を持ちます。
  • インストール時に、依存一覧からpip3で導入します。
  • 実行時に、レシピの設定値を環境変数へ渡し、ソースの場所を指定してエントリポイントを起動します。
  • バージョン(0.0.0)とアーティファクトのURIは仮の値です。将来のデプロイ処理が書き換える前提で、今回は仮のままにします。
タスク6: ビルドスクリプト(TDD)

コンポーネントを配布用のzipにまとめます。テストは1件で、外部コマンドの実行を偽物に差し替えて行います。

  1. コンポーネントの定義ファイルからバージョンを読みます。
  2. uvで開発用を除いた依存一覧を書き出します。
  3. ソース、レシピ、依存一覧を作業用フォルダに集めます。
  4. コンポーネント名とバージョンで分けたフォルダにzipとして保存します。

コマンドラインからはコンポーネント名を1つ指定して実行します。最後に、実際にスクリプトを動かしてzipが生成されることを確認します。
