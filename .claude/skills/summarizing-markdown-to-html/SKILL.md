# Markdown を要約して HTML 化する

## Overview

AI が出力した長い Markdown は、人間が読み通すのが難しい。
高い抽象度の要約と図を先頭に置き、詳しく知りたい人だけが開ける詳細を、1枚の自己完結 HTML にまとめる。

**原則:** 読者は忙しい人間。最初の画面だけで「何のためのもので、全体はどう動き、何を判断すべきか」が分かること。

## 入力と出力

- 入力: Markdown ファイルのパス。指定がなければユーザーに1回だけ確認する。
- 出力: **元ファイルと同じディレクトリ**に `<元のファイル名(拡張子なし)>.html` を書く。
- 既に同名の HTML がある場合は上書きしてよい。ただし、元 Markdown 自体は変更しない。
- 単一ファイルで完結させる。外部 CDN、外部フォント、外部画像は使わない。

## 手順

1. 元 Markdown を最後まで読む。
2. `template.html`(このスキルと同じディレクトリ)を読む。CSS と骨組みはそれを使う。
3. 下の「ページ構成」に沿って `{{BODY}}` の中身を組み立てる。
4. 次の3つのプレースホルダを置換した HTML を Write で出力する。
   - `{{TITLE}}`: 元文書の最初の H1。なければファイル名。
   - `{{SOURCE}}`: 元ファイル名のみ(プレーンテキスト)。
   - `{{BODY}}`: 下の「ページ構成」で作る `<section>` の並び。
5. 出力後、`{{` が残っていないことを `grep -n '{{'` で確認する。
6. ファイルの絶対パスを報告し、`open <パス>` で開けることを添える。

## ページ構成

`{{BODY}}` は次の順に並べる。

| 順 | セクション | id | 内容 |
|----|-----------|----|------|
| 1 | 結論(TL;DR) | `tldr` | 2〜4文。何のための文書で、結論や推奨は何か。 |
| 2 | 全体像(図) | `overview` | 仕組みや流れを表す図を1〜2枚。 |
| 3 | 要点 | `points` | 3〜7項目。1項目は1〜2文。 |
| 4 | 判断・対応が必要な点 | `actions` | 人間が決める、確認する、実行する項目。なければ「なし」。 |
| 5 | 詳細 | `details` | 元文書の主要セクションごとに `<details open>` で並べる(読者が閉じられる)。 |
| 6 | 元ファイル | `source` | 元 Markdown への相対リンク(ファイル名のみ)。 |

- 各セクションは `<section id="..."><h2>...</h2>...</section>` で書く。
- 結論だけ `<section id="tldr" class="tldr">` にする。
- テンプレートの目次(`<nav class="toc">`)の項目は、出力するセクションと一致させる。図を出さない場合は「全体像」の項目を目次から消す。
- 「判断・対応が必要な点」には、元文書の未決事項、要確認、未検証、未確認の記述をすべて入れる。
- 詳細の `<details>` は入れ子にしない。表と callout は入れてよい。
- `<details>` はすべて `open` 属性を付け、最初から開いた状態で出力する。閉じるかどうかは読者が決める。
- 比較や一覧は `<table>` にする。手順は `<ol>` にする。
- 注意や警告は `<div class="callout warn">` 、補足は `<div class="callout info">` を使う。

## 抽象度

読者に最初に渡すのは「目的、仕組み、理由、判断」であり、実装の部品ではない。

| セクション | 書くこと | 書かないこと |
|-----------|---------|-------------|
| 結論、要点 | 目的、方針、理由、範囲、トレードオフ | ファイル名、関数名、コマンド、設定値 |
| 全体像 | 登場するものと、その間の流れ | 内部の実装手順 |
| 詳細 | 各セクションの「何を、なぜ」を言葉で | ディレクトリ構成、コード、コマンドの全文 |

- 要点の1項目は「〜のために〜する」の形にする。手段より先に目的を書く。
- 識別子やコマンドは、読者が判断に使うものだけ本文に出す。例は、環境変数名や、事前に用意すべきリソース名。
- 詳細でも、コード、コマンド、ディレクトリツリーは原則として言葉に直す。読者が実行またはコピーして使うものだけ `<pre><code>` で残す。
- 削った技術詳細は、「元ファイル」セクションで元 Markdown を案内して補う。

## 図

図は、文章で説明すると長くなる「構成」「流れ」「関係」を1枚で見せるために使う。

- HTML にインライン SVG で書く。外部の画像や描画ライブラリは使わない。
- 1〜2枚にする。デプロイと実行時のように、視点が異なる流れは図を分ける。
- 1枚あたりのノードは最大8個。矢印は処理やデータの向きを表す。
- ノードの文字は短くする。主ラベルは全角10字程度まで、補足は1行にする。
- 元文書にない登場物や関係を足さない。
- 色は CSS クラスで指定する(`node`、`node accent`、`node warn`、`group`、`edge`)。ダークモードで色が崩れないように、色を直接書かない。
- 各 SVG に `role="img"` と `aria-label` を付け、図の意味を1文で書く。
- 図ごとに `<h3>` で見出しを付ける。
- 矢印の `marker` の `id` は、図ごとに変える(`arrow1`、`arrow2`)。

最小の例(左から右へ流れる3ノード)。座標は `viewBox` 内の値で、文字は `text-anchor="middle"` で箱の中央に置く。

```html
<div class="diagram">
<svg viewBox="0 0 560 110" role="img" aria-label="開発機から S3 を経由してデバイスへ届く流れ">
  <defs><marker id="arrow1" viewBox="0 0 10 10" refX="9" refY="5" markerWidth="8" markerHeight="8" orient="auto-start-reverse"><path d="M0 0L10 5L0 10z"/></marker></defs>
  <rect class="node" x="10" y="20" width="140" height="64" rx="10"/>
  <text x="80" y="48" text-anchor="middle">開発機</text>
  <text class="sub" x="80" y="68" text-anchor="middle">ビルド</text>
  <line class="edge" x1="150" y1="52" x2="210" y2="52" marker-end="url(#arrow1)"/>
  <text class="sub" x="180" y="44" text-anchor="middle">送信</text>
  <rect class="node accent" x="210" y="20" width="140" height="64" rx="10"/>
  <text x="280" y="48" text-anchor="middle">S3</text>
  <text class="sub" x="280" y="68" text-anchor="middle">保管</text>
  <line class="edge" x1="350" y1="52" x2="410" y2="52" marker-end="url(#arrow1)"/>
  <rect class="node" x="410" y="20" width="140" height="64" rx="10"/>
  <text x="480" y="48" text-anchor="middle">デバイス</text>
  <text class="sub" x="480" y="68" text-anchor="middle">実行</text>
</svg>
</div>
```

- 枠でまとめたい範囲は `<rect class="group" ...>` を、ノードより先に描く。枠のラベルは `<text class="cap">` を使う。
- 矢印の間隔が狭いときは、矢印ラベルを省くか、間隔を広げる。ラベルが箱や矢印に重ならないことを座標で確かめる。

## 忠実性のルール

要約は元文書を写すものであり、書き換えるものではない。

- 元文書にない事実、数値、結論を足さない。
- 数値、固有名詞、コマンド、パス、バージョンは、書くときは元のままにする。
- 元文書が不確かと述べている点は、不確かなまま書く。断定に変えない。
- 元文書が日本語以外でも、要約は日本語で書く。コード中の識別子は翻訳しない。
- 抽象化は言い換えであり、内容の追加ではない。抽象化のために、元文書にない目的や背景を作らない。

## HTML のルール

- 本文中のテキストは必ず HTML エスケープする(`<` `>` `&`)。元文書にタグ風の文字列があっても壊れないようにする。
- `<script>` は原則使わない。使うのは、読者の操作に必要なときだけとする。
- スマホ幅と印刷でも崩れないこと。テンプレートの CSS を削らない。
- 見た目の調整は `<style>` の末尾に足す。テンプレートの既存ルールは書き換えない。

## よくある失敗

| 失敗 | 対処 |
|------|------|
| 元の見出しを全部並べただけになる | 要点は3〜7項目に絞る。細部は詳細に回す。 |
| 要点にファイル名やコマンドが並ぶ | 目的と理由に書き直す。識別子は判断に必要なものだけ残す。 |
| 詳細に元文書のコードやツリーを丸写しする | 言葉に直す。使うものだけ残し、残りは元ファイルへ誘導する。 |
| 図が箱だらけで読めない | 8ノード以内にする。視点が違うなら図を分ける。 |
| 図の文字が箱からはみ出す | 主ラベルを短くする。箱の幅を広げる。 |
| 図に元文書にない要素が入る | 元文書に書かれた登場物と関係だけにする。 |
| 結論が最初の画面にない | TL;DR を先頭に置く。前置きを書かない。 |
| `<details>` が閉じた状態で出る | すべての `<details>` に `open` を付ける。 |
| 出力先が作業ディレクトリになる | 必ず元ファイルと同じディレクトリに書く。 |
